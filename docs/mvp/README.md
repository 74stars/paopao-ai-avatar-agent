## 2. MVP 目标

交付一个可在 Windows 10/11 x64 与 macOS 12+（x64/arm64）安装和运行的本地优先桌面应用，稳定完成以下闭环：

```text
桌面文字
  -> 原文和任务在同一 SQLite 事务中持久化
  -> 后台任务可重试、可恢复
  -> 一个真实 AI Provider 返回受 Schema 约束的派生结果
  -> 活书房展示真实列表、详情、状态和来源
  -> 用户可以搜索、纠正、重跑、删除和导出
```

MVP 验证两个假设：

1. 常驻桌面入口是否足够轻，用户愿意持续记录。
2. 自动整理、来源追溯和活书房是否比普通笔记列表更有长期价值。

### 2.1 用户可见术语

- `记录内容`：用户当前认可的记录版本；编辑会创建 revision，不会覆盖最初输入。
- `最初记录`：首次保存的不可变内容；只在记录发生过编辑时作为历史依据显示。
- `AI 整理`：分类、摘要、实体、目标和下一步；它是派生信息，不能替代记录内容。
- `记录方式`：桌面泡泡或飞书等录入入口。
- `整理依据`：AI 结论引用的本条记录或关联记录片段。

`rawText`、`currentText`、`derivation` 和 `source` 是工程契约名称，不直接作为用户界面标题。

## 3. 成功口径

MVP 的首要指标不是模型回复质量，而是可信记录闭环。必须满足：

- 保存确认延迟：在 Windows 与 macOS 参考机上，从用户提交到 UI 渲染 `stored` 的端到端 P95 小于 300ms，不等待 AI；同时单独记录 SQLite 事务耗时，用于定位性能回归。
- 数据可靠性：已返回 `stored` 的原文在断网、AI 失败、强退和重启后仍可查看。
- 处理可恢复性：可重试任务在重启后恢复；同一幂等键不会产生两条 Entry。
- 可追溯性：每个 AI 派生结果都能回到 Entry 和原文证据。
- 可控性：用户能调整 AI 分类和摘要、手动重跑、删除记录并导出数据。
- 数据真实性：生产书房不存在硬编码数量、示例记录或伪造报告。
- 发布可用性：干净 Windows 10/11 x64 与 macOS 12+ x64/arm64 环境完成安装、首次启动、保存、重启恢复和卸载；窗口交互没有 P0 缺陷，并已为当前候选保存跨平台截图与对应的人工美术指导记录。

指标口径统一使用脱敏的结构化日志和测试结果；日志不得保存原文、完整 Prompt、密钥或飞书凭据。

## 4. 范围

### 4.1 必须交付

| 能力 | MVP 结果 |
|---|---|
| 桌面壳 | 透明桌面泡泡、托盘、全局快捷键、快速记录窗口、活书房、设置页 |
| Capture | 仅文字；桌面入口调用统一 `CaptureService` |
| 本地数据 | SQLite 迁移、启动备份、Entry、Job、派生结果、来源和 FTS5 |
| 后台处理 | 持久化任务、租约、重试退避、启动恢复、失败状态和手动重跑 |
| AI | 多个命名配置、单 active Provider、Direct OpenAI 兼容协议或复用 Codex 渠道；结构化抽取、Zod 校验、一次修复重试、调用审计；用户显式选择 `think` 时生成有来源洞察 |
| 书房 | 真实分页列表、详情、全文搜索、来源、状态、分类纠正、派生内容编辑 |
| 数据控制 | 单条删除、重新处理、JSON/Markdown 导出、错误诊断导出 |
| 安全 | `contextIsolation`、最小 preload API、IPC Schema、`safeStorage`、日志脱敏 |
| 产品化发布 | 固定依赖、截图采样、渲染/交互回归、Windows x64 NSIS 与 macOS x64/arm64 DMG/ZIP 包、干净机冒烟 |

### 4.2 明确不做

- 语音、图片、链接抓取、PDF、DOCX 和其他文件处理。
- Embedding、向量数据库和混合检索。
- 日报、周报、主动提醒、日历、天气和外部行动执行。
- Paopao 自有云服务、Supabase 同步、多设备和冲突合并。
- 飞书连接器的正式发布、真实租户验收、OAuth、应用市场分发、文档/日历/通讯录、多个租户或多个账号。
- 内置模型下载、模型市场、同时调用多个 active Provider 或 Provider 自动路由；用户仍可显式配置 loopback OpenAI 兼容端点。
- Self Model/人格画像的自动抽取、确认和回写；MVP 不把单条输入推断成长期人格事实。
- 在线预览接入真实本地数据。`preview/` 始终使用演示数据。
- SQLite 整库/字段级应用层加密。MVP 依赖操作系统用户账户和磁盘安全；设置页必须明确说明原文以本地数据库形式保存，`safeStorage` 只保护凭据。

## 5. 当前工程基线

截至 2026-08-11，本地 MVP 功能闭环已经实现：

- 根 npm workspace、单一 lockfile、类型检查、构建、CI 和 Electron 安全边界已建立。
- Capture、SQLite 迁移、持久任务、启动恢复、AI 整理、洞察、FTS、纠正、删除、导出和备份恢复已接入真实运行路径。
- AI Provider 支持多个命名配置、单 active Provider、OpenAI 兼容协议和 Codex 渠道复用；凭据通过 write-only IPC 和 `safeStorage` 管理。
- 活书房使用真实 SQLite 列表、详情、数量和搜索结果。飞书实现保留为已验证的 MVP 后增量。
- 当前全量自动化与 macOS arm64 Electron E2E 通过；详细计数和候选报告只在 [`gate-status.md`](./gate-status.md) 维护。

当前首要风险不是功能空缺，而是交付基线：`HEAD` 与 `origin/main` 仍停在 `c08fa15`，大量 MVP 源码、测试和 CI 文件尚未进入 Git。远端提交目前无法重建通过验证的本地候选。

G4 仍未完成。macOS x64、Windows x64、干净机安装、真实 OS 指针拖动、公开签名/notarization 和持续视觉迭代仍是发布阻塞项。

## 6. 核心用户验收场景

### S1 桌面保存与恢复

1. 用户用 `Ctrl+Shift+Space` 打开快速记录并提交文字。
2. 默认模式为 `remember`；用户可显式切换 `think`，但两种模式都先完成同一个本地保存事务。
3. UI 在本地事务提交后显示“已保存，等待整理”。
4. 用户断网并强制结束应用。
5. 重启后原文仍在，任务处于等待联网或可重试状态；离线等待不消耗重试次数。
6. 网络恢复后任务继续，不产生重复 Entry。

### S2 AI 失败与纠正

1. Provider 返回超时、限流或无效 JSON。
2. 原文仍可查看，任务显示可诊断状态。
3. 自动重试耗尽后进入 `failed_final`，用户可以手动重跑。
4. 成功后详情页显示摘要、分类、实体、目标、行动和原文来源。
5. 用户修改分类或摘要，系统生成新 revision，并保留 `created_by=user` 审计信息。
6. `think` 模式的洞察异步完成且引用真实来源；洞察失败不回滚已经完成的结构化记忆。

### S3 搜索、删除和导出

1. 用户能用原文或派生摘要中的精确关键词搜索。
2. 搜索结果可打开原文和来源。
3. 删除后该记录不会出现在列表、搜索或新导出中，相关派生数据被清理。
4. 导出包含版本、校验清单、原文、派生结果和必要元数据，不包含密钥和日志。

用户此前主动创建并复制出的导出是独立快照，删除当前记录不会远程修改这些副本；删除确认必须明确提示这一点。

### S4 飞书在线输入（MVP 后增量，不参与本期签收）

1. 用户在设置中保存飞书凭据并建立长连接。
2. 桌面端生成短时一次性绑定码，用户发送 `/bind <code>`。
3. 绑定成功后，飞书文本通过统一 `CaptureService` 写入本地 SQLite。
4. 飞书默认 `ack_only`：只发送一次保存确认；用户在设置中选择 `insight` 后才为每条文本异步发送一次带来源结果。
5. 同一飞书 message 的重复 event 只对应一个 Entry；自动重放和恢复时，保存确认和最终结果各至多一次。
6. ambiguous 投递默认不自动重发；用户可标记已发送，或在明确知晓可能重复后执行一次人工重试。
7. 应用退出后界面和说明明确显示飞书离线，不承诺代收。

### S5 Wave 4 产品化与跨平台发布

1. A6 记录候选 Git SHA 并生成固定状态截图矩阵；SHA 只用于追踪构建，不作为美术基线。人工评审基于当前画面输出下一轮美术指导。
2. 三个窗口的拖动区域、控件命中、焦点和关闭逻辑通过交互回归；泡泡拖动不触发点击。
3. 泡泡双击只打开活书房，单击只在双击窗口结束后切换快速记录，双击不触发单击。
4. 干净 Windows 10/11 x64 机器安装 NSIS 包，完成迁移、保存、重启恢复和卸载。
5. 干净 macOS 12+ x64/arm64 机器安装 DMG/ZIP 包，完成迁移、保存、重启恢复和卸载。
6. 产物签名/notarization 状态、SHA-256 和数据保留策略均有发布记录。

## 7. 全局工程规则

1. 原文先存：任何模型请求都发生在本地事务提交之后；未来外部 Adapter 也必须遵守。
2. 原文不可静默修改：用户编辑和 AI 结果都作为 revision 或 derivation。
3. 单一写路径：桌面和测试夹具调用同一个 `CaptureService`；未来外部 Adapter 不得另建写路径。
4. SQLite 是唯一权威源：UI 状态、数量和搜索结果不得来自内存假数据。
5. Core 不依赖 Electron：Electron 只负责组合、窗口、IPC、安全存储和生命周期。
6. Renderer 不可信：不能直接访问 Node、数据库、文件系统、密钥读取接口或原始 `ipcRenderer`；凭据只允许由用户通过 write-only IPC 瞬时提交。
7. 接口先行：跨 Agent 字段只能在 `contracts.md` 和共享 Schema 中定义。
8. 失败可见：不吞错；对用户给稳定错误码和恢复动作，对日志给脱敏诊断上下文。
9. 幂等优先：外部事件、定时恢复和用户双击都必须能安全重复执行。
10. 范围克制：MVP 没有进入范围的能力不创建占位 UI 承诺。

## 8. 完成定义

只有同时满足以下条件，MVP 才能标记完成：

1. 本目录所列 S1-S3 与 S5 全部通过并保存验收证据；S4 不参与 MVP 签收。
2. 所有 MVP P0/P1 工作包完成，没有以 mock 替代生产实现；M3 的 `increment P0` 不计入本期签收。
3. `typecheck`、单元测试、数据库集成测试、Renderer build、Electron build、Windows 打包和 macOS DMG/ZIP 打包全部通过。
4. Renderer 安全边界、日志脱敏、密钥存储和删除完整性测试通过。
5. AI 失败、断网、强退和重启均有自动化或明确的手工验收记录。
6. README 的“已实现 / 规划”与实际能力一致。
7. 安装包附带版本、SHA-256、已知限制和数据保留说明。

## 9. 延后决策

以下问题不阻塞 MVP，也不允许 Agent 自行提前实现：

- 是否加入向量检索：等 FTS5 的真实检索数据后决定。
- 是否支持 OpenAI 兼容协议以外的 Provider 插件：等现有 Direct/Codex 配置的可靠性数据后决定。
- 是否建设云同步：等单机数据模型和导出恢复稳定后决定。
- 是否加入多模态、报告和提醒：等文字闭环留存与纠错数据后排序。
- 是否发布飞书连接器，以及采用自建应用向导还是公开应用 OAuth：MVP 后根据个人用户需求单独决策。
