# Wave 4 产品化与跨平台发布

> 状态：ACTIVE
> 范围：桌面候选画面迭代、窗口交互、Windows/macOS 构建与发布

## 1. 权威边界

工程文档和自动报告不定义当前目标风格。候选 commit SHA 只用于复现构建，不能成为视觉权威。

程序可以在固定环境中生成截图、像素数据和渲染统计。这些结果只用于确认截图可信、资源已加载、画布非空、透明通道和裁切正常，以及交互路径可执行。软件不得据此输出美术 PASS/FAIL、风格合格率或设计完成结论。

实际视觉评审只面对当前运行候选和本轮用户提供或确认的参考。每次评审都必须产生下一轮指导，而不是以“审核通过”为目标。

## 2. 每轮画面迭代

A3 提交可运行候选。A6 记录 commit、平台、窗口尺寸、DPR、数据状态和未裁切原始截图，不做美术裁决。

截图至少覆盖：

- 桌面泡泡的 quiet、listening、thinking、insight 状态；
- 活书房的空、加载、错误、真实记录和阅读层状态；
- 1366x768、1440x900、1920x1080；
- macOS 与 Windows 的目标缩放环境。

每轮人工美术评审记录必须包含：

1. 当前画面的整体判断和主要矛盾；
2. 按影响排序的具体问题；
3. 每个判断对应的画面证据；
4. 本轮应保留的有效部分；
5. 下一轮可执行的美术指导；
6. 仍需通过新候选验证的未知项。

记录中不设置“美术 PASS”“风格达标率”或自动关闭条件。下一轮是否继续、改变方向或进入实现，由用户基于实际画面决定。

## 3. 工程检查

自动化与 QA 可以对以下事项给出工程 PASS/FAIL：

- 截图是否来自真实应用和指定状态；
- 资源是否解码、加载并覆盖预期视口；
- Canvas 是否非空，透明窗口是否出现非预期底色；
- 文本、控件和场景对象是否裁切、溢出或互相遮挡；
- 键盘、指针、raycast、滚动和业务动作是否可达；
- DPR、内存、帧循环和 renderer error 是否满足运行要求。

工程检查报告必须使用“渲染完整性”“交互完整性”或“发布工程检查”等名称，不能称为美术审核或视觉签收。

## 4. 窗口交互

| 窗口 | 可移动区域 | 交互区域 | 工程要求 |
| --- | --- | --- | --- |
| 泡泡 | 泡泡主体拖动 | 主体点击 | 拖动超过阈值不触发 click；窗口位置随指针移动 |
| 快速记录 | 顶部 header | 关闭、模式切换、输入、保存 | header 可拖动；按钮和输入不移动窗口 |
| 活书房 | 明确的窗口移动区域 | 场景对象、搜索、设置、列表、详情 | 移动区域不吞掉控件；滚动区域不移动窗口 |

泡泡点击状态机：

```text
pointer down -> (移动超过阈值 ? DRAG : MAYBE_CLICK)
MAYBE_CLICK + 第二次点击在 doubleClickInterval 内 -> DOUBLE(open library)
MAYBE_CLICK + interval 到期 -> SINGLE(toggle capture)
DRAG -> pointer up（不产生 SINGLE/DOUBLE）
```

自动化可以验证事件序列；原生 app-region 拖动仍需在目标平台使用真实 OS 指针检查。

## 5. 跨平台发布

| 平台 | 包格式 | 必测项 |
| --- | --- | --- |
| Windows 10/11 x64 | NSIS | 安装、托盘、快捷键、拖动、双击、SQLite ABI、卸载数据策略 |
| macOS 12+ x64 | DMG + ZIP | 首次打开、透明窗口、权限、快捷键、拖动、双击、SQLite ABI |
| macOS 12+ arm64 | DMG + ZIP | 同上；不能只在 Rosetta 下验证 |

无签名或 notarization 凭据时只生成内部候选包，不能标记为公开 Release。发布记录包含 artifact SHA-256、架构、签名状态、数据库版本和已知限制。

## 6. 分工

| Owner | 职责 | 不拥有的权力 |

## 7. 发布出口

工程发布 Gate 要求真实数据、安全、交互、安装、恢复和跨平台检查通过。候选画面必须附带最近一轮原始截图与人工美术指导记录，不能附带软件生成的美术通过声明。

产品是否采用当前候选不由自动 Gate 决定。用户可以继续要求美术迭代，即使全部工程检查已经通过。
